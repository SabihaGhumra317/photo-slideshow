# Assumptions and trade-offs

1. **Identity:** 32 random bytes in an HttpOnly SameSite=Lax visitor cookie; only SHA-256 of its bytes in MySQL. Six-character, 32-symbol visitor code is an optional recovery fallback. Its HMAC is stored with `APP_SECRET`. Since six-character codes are guessable, restoration is IP-rate-limited and rotates the browser token (logging out an earlier browser). Losing both credentials makes the prior identity unrecoverable. Shared codes act like passwords.
2. **Approval is mandatory:** Every first-time or returning visitor's uploaded photo starts `pending` and is privately stored. An admin manually approves each photo; nothing enters the public slideshow before approval. `approved` photos can be separately hidden. `rejected` photos stay stored until deleted or expired, so the visitor can see their status. There is intentionally no moderation-off switch.
3. **Public screen:** “Immediately” means within roughly 2.5–3 seconds **after admin approval**, assuming browser and network are active. It does NOT mean immediately after upload. The TV does not need refreshing; browser scheduling can delay polls.
4. **Queue:** New approvals interrupt the TV and play first. The client then shows that visitor's other approved photos before the rest. The API sends the complete approved set; this detects newly approved older photo IDs as well as deletions/hides. A browser refresh starts a fresh cycle without historic priority state. Limit of 500 approved slides per poll, to keep payload bounded.
5. **Duration:** 8 seconds initially; admin may set 3–60 seconds. Images use fade and gentle zoom; next image is preloaded.
6. **Consent:** Mandatory opt-in on account creation; version `2026-11-v1`, timestamp and keyed IP digest recorded. A visitor can withdraw consent and delete all photos. Re-consent is required before later uploads. `APP_SECRET` is also used for recovery code hashes.
7. **Retention:** 90 days by default; configurable 1–3650 days. A Windows Task Scheduler job must run `scripts/cleanup.php`. Without a scheduler, automatic expiry does not occur.
8. **Limits:** JPG/PNG/WEBP actual MIME and image dimensions checked, GD re-encodes to max 1920px (strips EXIF). 5 MiB per input, 5 uploads per request, 20 retained photos per visitor. Animated WebP is flattened. The server needs PHP GD, fileinfo, pdo_mysql and mbstring; PHP limits must be set high enough.
9. **Concurrency:** `SELECT ... FOR UPDATE` locks the visitor row during a multi-photo transaction, preventing concurrent requests bypassing the 20-photo quota. Each file gets a random 20-byte filename. DB timestamps plus IDs give stable ordering. Orphan files are removed on upload failures; disk and database are not part of one atomic transaction, so sudden process crashes can still leave files needing manual reconciliation.
10. **Admin:** Single local admin username `sabiha`, password configured only in private `.env` and hashed via `password_hash()` using the CLI seed script. Session login, CSRF and IP-based failed-login throttling. Use a strong unique password; simple demo passwords are not safe on public networks.
11. **Languages and theme:** English default, Hindi and Gujarati translations for core visitor screens; administrator screens are in English. Language choice in cookie; theme starts from OS preference and persists explicit choice in localStorage.
12. **Privacy limitation:** Public screen photos can be photographed or copied by bystanders. File deletion cannot revoke external copies or cached images. Apache `uploads/.htaccess` prevents scripts executing there; for internet deployments move photos fully outside web root and serve via authorization-aware endpoints. `uploads` URLs are publicly reachable if guessed; filenames are cryptographically unpredictable. HTTPS is required for real remote use.
13. **No external framework:** Pure PHP 8.x, MySQL/PDO, vanilla JS and CSS. Google Fonts are optional; system fonts are used offline. Application paths assume `/photo-slideshow` on WampServer.

## Upload batch limit (updated requirement)

A newly registered visitor can submit **at most three photos in their first successful upload request**. After that, all requests are limited to **one photo at a time**; entering a visitor code to restore identity also enforces the returning-visitor one-photo rule, even if there were no prior uploads. The total retained photo allowance of 20 per visitor still applies. All new images remain pending admin approval. A browser-side limit improves usability; PHP independently enforces it. First upload consumption is recorded in the existing upload attempt log in the same transaction as photo creation to handle concurrent uploads.
